# urpc Constitution

urpc 是一个跨平台、gRPC 兼容的 RPC 框架：基于 libuv（异步事件循环）、
nghttp2（HTTP/2）与 upb（protobuf 运行时）构建，使用 C++17 开发、
CMake 构建。第一阶段仅交付 C++ 语言支持，但公共 API 设计必须为后续
多语言绑定（Python、Lua 等脚本语言）预留演化空间。本宪法对项目全部
规格、计划与代码变更具有约束力。

## 核心原则（Core Principles）

### I. gRPC 线协议兼容（不可妥协）

urpc 必须与 gRPC 线协议保持兼容；兼容性优先于功能丰富度与实现便利性。

- 必须实现 gRPC over HTTP/2 的完整语义：长度前缀消息帧、gRPC 状态码、
  trailer、metadata、超时/截止时间（deadline）传播。
- 任何版本合入前，必须通过针对官方 gRPC 客户端/服务端的互操作
  （interop）测试套件。
- 禁止引入与官方 gRPC 实现不兼容的私有协议扩展；确需扩展时，必须先
  修订本宪法。

**理由**：与 gRPC 生态互操作是本项目存在的根本价值；失去线协议兼容，
urpc 将退化为另一个自成体系、无法互通的 RPC 系统。

### II. 分层内核与可绑定 API 边界

运行时内核与用户可见 API 必须分层，且边界必须可被脚本语言绑定。

- 内核（libuv 事件循环封装、nghttp2 会话管理、upb 消息编解码）必须与
  面向用户的 C++ API 分离；内核不得依赖上层 API。
- 跨模块边界（内核与 API 层之间、未来的绑定层与内核之间）不得泄漏
  异常、STL 类型或所有权语义；面向未来绑定的边界必须保持稳定、
  C 兼容（C-ABI）的接口形态。
- 第一阶段仅交付 C++ API，不交付绑定代码；但每一项公共 API 决策必须
  评估其对 Python、Lua 等后续语言绑定的成本影响。

**理由**：多语言支持是既定路线图。若第一阶段以 C++ 便利性填满边界，
后续每种语言绑定都要付出内核改造的代价。

### III. 跨平台构建纪律

跨平台是构造出来的属性，不是事后移植出来的补丁。

- urpc 必须在全部受支持平台（至少 Linux、macOS、Windows）上以 CMake
  作为唯一构建系统完成构建并通过测试。
- 平台相关代码必须收敛到独立的平台抽象模块中；禁止在通用逻辑内散布
  条件编译。
- 任何变更合入前，全部受支持平台与受支持编译器的 CI 构建必须为绿。

**理由**：libuv、nghttp2、upb 均具备跨平台能力，框架自身不应成为短板；
平台分支散布会成倍放大维护与测试成本。

### IV. 测试背书的变更（不可妥协）

每一项行为变更必须由自动化测试背书；测试套件是硬性合入门禁。

- 单元测试统一基于 GoogleTest（gtest 断言与 gmock 桩件）编写；禁止
  引入第二套单元测试框架。
- 性能测试统一基于 Google Benchmark；性能敏感路径（事件循环、HTTP/2
  编解码、消息序列化、内存分配）必须附带基准用例，基准必须可重复
  运行且可跨版本对比。
- 单元测试覆盖组件行为，集成测试覆盖客户端/服务端交互，互操作测试
  覆盖与官方 gRPC 的对端通信；三类测试缺一不可。
- 缺陷修复必须先提交可复现该缺陷的回归测试，再提交修复。
- 测试门禁失败时禁止合入；禁止通过跳过或删除失败测试来"变绿"。

**理由**：RPC 框架的正确性依赖协议细节与时序行为，人工审查无法替代
可重复执行的验证；统一的测试与基准工具链保证结果可对比、可追溯，
互操作测试同时是原则 I 的执法机制。

### V. 依赖最小化且边界固定

第三方运行时依赖集合固定为：libuv、nghttp2、upb（及其文档化的传递
依赖）；开发/测试依赖集合固定为：GoogleTest、Google Benchmark。

- 未经宪法修订，禁止引入任何新的直接依赖（运行时与开发/测试类别
  均适用）；引入申请必须说明体积、许可证、维护状态与跨平台支持
  情况。
- 开发/测试依赖（GoogleTest、Google Benchmark）不得链接进或随同
  发布任何运行时构件。
- 依赖的引入方式（系统安装或源内 vendoring）与版本必须固定并经评审。
- 能用既有依赖实现的功能，禁止为新功能引入新依赖。

**理由**：依赖面即审计面与构建风险面；依赖膨胀会直接侵蚀跨平台能力
（原则 III）与可部署性；测试栈独立成固定边界，既满足原则 IV 的工具
链统一要求，又不污染运行时。

## 技术栈与兼容性约束

- 语言标准：C++17。合入依赖 C++20 及以上特性的代码视为违宪，除非
  先修订本条目。
- 构建系统：CMake 为唯一构建入口；标准配置通过 CMake presets 提供。
- 运行时依赖：libuv（异步 I/O 事件循环）、nghttp2（HTTP/2）、
  upb（protobuf 运行时）。
- 测试栈（仅开发/测试依赖，不进入运行时构件）：单元测试 GoogleTest
  （gtest/gmock），性能测试 Google Benchmark。
- 协议基线：gRPC over HTTP/2；协议行为以官方 gRPC 实现为参考基准。
- 阶段范围：第一阶段仅支持 C++ 语言。Python、Lua 等多语言支持是现在
  的设计约束（见原则 II），不是现在的交付物。

## 开发流程与质量门禁

- 本项目采用 Spec Kit 规格驱动开发：`/speckit.specify` 与
  `/speckit.plan` 产出的每个工件必须包含宪法符合性检查
  （constitution check），逐条对照原则 I–V。
- CI 必须在全部受支持平台与受支持编译器矩阵上执行构建、GoogleTest
  测试套件（单元/集成/互操作）与 Google Benchmark 基准；矩阵全绿是
  合入的必要条件，基准结果必须留档以供跨版本对比。
- 与官方 gRPC 的互操作测试套件是发布门禁；未通过互操作套件的版本
  禁止发布。
- 变更说明（PR/commit）必须声明其触及的原则条目；评审人对原则符合性
  拥有否决权。

## 治理（Governance）

- 本宪法是项目最高治理文件，效力高于任何惯例、口头约定与其他文档；
  与宪法冲突的规格、计划或代码，必须先行修订宪法或修改变更本身。
- 修订程序：任何修订必须以书面提案提出，包含动机与对既有规格、代码
  的影响分析，并按语义化版本规则升版：
  - MAJOR：原则的移除或向后不兼容的重定义；
  - MINOR：新增原则，或实质性扩写既有章节；
  - PATCH：澄清、措辞与笔误修正。
- 合规审查：宪法符合性在 specify、plan、code review 三个环节强制
  检查；原则 I 与原则 IV 标记为不可妥协（NON-NEGOTIABLE），违反即
  阻断合入。
