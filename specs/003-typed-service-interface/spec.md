# Feature Specification: 类 gRPC 的类型化服务接口（Typed Service Interface）

**Feature Branch**: `003-typed-service-interface`

**Created**: 2026-09-11

**Status**: Draft

**Input**: 用户描述："实现类 gRPC C++ 的最终接口，工具生成服务端纯虚接口类
IxxxService，客户端生成 XxxServiceProxy 继承同一个接口（保留 Channel
表示连接，保留 Client 用于控制面的功能，Proxy 是业务面接口）；用户实现
服务端业务只需要继承相应接口类 XxxService，重写相关方法；然后将
XxxService 类的实例注册到 Server 上即可。"

## Constitution Check

- **原则 I（gRPC 线协议兼容）**：本特性仅重塑用户侧编程接口，不改动线
  协议行为；线格式、状态码、trailer、deadline 语义保持不变，与官方
  gRPC 对端的互通测试继续作为验收门禁。
- **原则 II（分层内核与可绑定 API 边界）**：接口生成与注册/代理机制
  完全位于 API 层之上，内核零改动；跨边界仍不泄漏异常与 STL 所有权
  语义，为后续语言绑定预留空间。
- **原则 III（跨平台构建纪律）**：生成器与生成物必须随标准 CMake 构建
  在 Linux/macOS/Windows 三平台通过；无平台分支散布。
- **原则 IV（测试背书的变更）**：接口形态、注册、代理调用全部由
  GoogleTest 单元/集成测试背书，并保留既有端到端示例与互操作测试；
  缺陷修复先提交可复现回归测试。
- **原则 V（依赖最小化且边界固定）**：生成器复用既有 vendored protoc
  与 upb 生成链，不引入任何新依赖；生成代码纳入既有构建与测试矩阵。

## 用户场景与测试（User Scenarios & Testing）

### User Story 1 - 服务端以接口继承方式实现业务 (Priority: P1)

服务端开发者拿到一份服务描述（如 `EchoService`），从工具生成的纯虚
接口类（如 `IEchoService`）继承出业务类（如 `EchoServiceImpl`），把每个
远程方法重写为一个普通的成员函数；业务类的一个实例整体注册到 Server
上，服务即可对外提供该方法集合。开发者不需要手写方法名字符串、消息
编解码或分发代码——这些全部由生成物与框架承担。

**Why this priority**: 这是本次接口重塑的核心目标与第一价值主张：把
"注册散装 lambda + 字符串路径" 的现状升级为 "实现一个接口类" 的
gRPC 风格体验；没有它，后续故事都没有落点。

**Independent Test**: 以接口继承方式实现示例 echo 服务的全部方法，注册
实例、启动服务端，从任一兼容客户端（含官方 gRPC 客户端）发起调用，
验证每个方法都被正确分发并返回正确响应。

**Acceptance Scenarios**:

1. **Given** 工具已从服务描述生成了 `IEchoService`（纯虚接口类），
   **When** 开发者继承它并重写全部方法、将实例注册到 Server，
   **Then** 服务启动后，对每个远程方法的调用都路由到对应重写方法，
   请求/响应消息自动完成编解码。
2. **Given** 业务类只重写了接口中的部分方法，**When** 客户端调用未被
   重写的方法，**Then** 客户端收到明确的「未实现（UNIMPLEMENTED）」
   状态，服务端其余方法不受影响。
3. **Given** 同一个业务实例已注册到某个 Server，**When** 再次注册同一
   服务名的另一实例到同一 Server，**Then** 注册被拒绝并返回明确错误
   （同一服务名不可重复注册）。
4. **Given** 业务方法内部可以感知调用上下文（取消状态、剩余时间等），
   **When** 客户端取消或截止时间到达，**Then** 方法能通过上下文感知并
   提前终止，客户端收到相应状态。

---

### User Story 2 - 客户端以代理对象调用业务方法 (Priority: P1)

客户端开发者从同一个服务描述获得代理类（如 `EchoServiceProxy`，继承
同一个 `IEchoService` 接口），从 Channel（表示一条到目标服务的连接）构
造代理后，直接以成员函数形式调用业务方法；同步与异步两种调用形态均
可用。开发者不接触方法名字符串，也不手工编码请求。

**Why this priority**: 与 US1 共同构成对称的接口体验；代理是客户端业务
面接口，是本特性的另一半核心。

**Independent Test**: 从 Channel 构造示例服务的代理，同步与异步调用每个
方法，验证响应与错误状态均正确返回；其中至少一次调用指向官方 gRPC
服务端以验证互通。

**Acceptance Scenarios**:

1. **Given** 一个已建立的 Channel 与服务描述对应的代理类，
   **When** 开发者从 Channel 构造代理并调用其方法，**Then** 调用被路由
   到远端服务，返回类型化响应或明确的失败状态。
2. **Given** 远端方法不存在或服务不可达，**When** 代理方法被调用，
   **Then** 调用方收到明确的错误状态（UNIMPLEMENTED/UNAVAILABLE），
   而不是无响应或含糊错误。
3. **Given** 同一 Channel 上构造的多个代理（可属不同服务），
   **When** 多线程并发通过代理发起调用，**Then** 各调用独立完成、结果
   正确配对（代理可并发使用）。
4. **Given** 客户端指定了调用截止时间，**When** 远端超时未回，**Then**
   调用在截止时间到达时以 DEADLINE_EXCEEDED 状态结束。

---

### User Story 3 - 接口与代理由工具生成 (Priority: P1)

开发者提供标准服务描述（含服务、方法与消息定义），构建过程自动产出
三件生成物：服务端纯虚接口类、客户端代理类、以及将两者桥接到框架的
支撑代码（类型转换/编解码/方法表）。生成物对用户是"像手写一样"可读、
可 include 的头文件，且随项目标准构建自动更新。

**Why this priority**: "工具生成"是接口体验的前提：接口与代理由同一份
描述派生，才能保证两端签名一致；这也是维持与 gRPC 服务描述生态兼容
的关键。

**Independent Test**: 修改服务描述（新增一个方法），重新构建后：服务端
接口类出现对应新纯虚方法（业务类编译错误提醒实现），代理出现对应新
方法，端到端调用通过。

**Acceptance Scenarios**:

1. **Given** 一份含 ≥2 个方法的服务描述，**When** 标准构建运行，
   **Then** 生成的接口类对每个方法恰好声明一个纯虚成员函数，代理类
   继承同一接口并提供对应调用成员。
2. **Given** 服务描述新增方法后重新构建，**When** 业务类未随之更新，
   **Then** 编译失败并明确指向缺失的重写（接口演进由编译器背书）。
3. **Given** 同一份生成物被服务端与客户端同时使用，**When** 一端调用
   另一端实现，**Then** 消息类型与行为一致（两端共享同一接口契约）。

---

### User Story 4 - 示例与存量测试切换到新接口 (Priority: P2)

echo 示例（服务端/客户端）与相关测试迁移到接口继承 + 代理调用形态，
成为新接口的活文档；现有能力（deadline、取消、优雅关闭、动态注册等）
在新形态下全部保持可用并通过测试。

**Why this priority**: 示例是框架的"第一体验"，也承担最外层回归验证；
不迁移则新旧两套风格并存会抵消接口重塑的价值。

**Independent Test**: 在全部受支持平台构建并运行迁移后的示例与全量
测试套件，断言往返正确、零失败。

**Acceptance Scenarios**:

1. **Given** 迁移后的 echo 示例，**When** 独立运行，**Then** 启动服务端
   （接口实现类）、以代理发起调用、打印成功结果并以零退出码结束。
2. **Given** 全量测试套件，**When** 在三平台 CI 上运行，**Then** 单元/
   集成/互操作/示例测试全部通过（不因接口切换丢失任何既有覆盖）。
3. **Given** 与官方 gRPC Python 对端的互操作测试，**When** 以新接口
   运行，**Then** 双向互通全部通过（线协议行为不变）。

---

### User Story 5 - 控制面与业务面分离 (Priority: P2)

开发者可以只关心业务：Channel 表示连接（地址、生命周期、关闭），
Client 承担控制面（连接管理、后续的负载/重试等控制策略挂载点），
Proxy 只暴露业务方法。三者职责清晰、不互相越界：关闭 Channel 使其上
所有代理的后续调用立即失败，业务接口不掺杂连接管理细节。

**Why this priority**: 用户明确要求的对象职责划分（Channel=连接、
Client=控制面、Proxy=业务面）；这是接口能长期演进的架构保障，但对
最小可用闭环而言比前三条略缓。

**Independent Test**: 构造 Channel → Client → Proxy 的组合，关闭
Channel 后验证代理调用得到明确失败；验证 Proxy 上不出现任何连接管理
类接口。

**Acceptance Scenarios**:

1. **Given** 从某 Channel 构造的代理正在使用，**When** 该 Channel 被关闭，
   **Then** 后续代理调用立即返回明确的失败状态，不挂起、不崩溃。
2. **Given** 框架公开 API 面，**When** 审视 Proxy 类型，**Then** 其上
   只有业务方法与业务参数（无 connect/close 等连接管理成员）。
3. **Given** 客户端开发者需要调整控制面行为（如消息大小上限），
   **When** 使用 Client/Channel 的控制面接口，**Then** 生效范围明确、
   不影响业务接口签名。

---

### Edge Cases（边界情形）

- 服务描述中未定义任何方法时，生成的接口/代理如何呈现（空接口可生成、
  可注册，调用面为空）？
- 同一 Server 注册多个不同服务的实例：必须全部可用、互不串扰；重复
  注册同一服务名必须被拒绝（US1 场景 3 已覆盖拒绝路径）。
- 业务类重写方法抛出异常时：框架不得让异常穿越边界（原则 II），
  调用以明确的 INTERNAL 状态结束，服务端进程不退出。
- 代理方法在框架事件循环线程内同步调用：保持既有快速失败语义
  （INTERNAL，禁止死锁），错误信息引导用户改用异步形式。
- 生成物与用户手写同名类型的冲突（命名空间隔离由生成器保证）。
- 服务描述的 message 与 service 分属多个文件时，生成器按文件对正确
  产出，include 关系可传递。
- 极端大消息（达到 max_receive_message_size 上限）经接口往返：行为
  与既有 API 一致（RESOURCE_EXHAUSTED），接口层不改变尺寸语义。

## 需求（Requirements）

### Functional Requirements

- **FR-001**: 系统 MUST 提供由服务描述自动生成服务端纯虚接口类的工具；
  每个远程方法在接口中对应一个纯虚成员函数，签名包含类型化请求消息、
  调用上下文与完成回调。
- **FR-002**: 客户端代理类 MUST 继承与服务端相同的接口类，并将每个
  接口方法实现为远程调用；同一份服务描述在两端产生同一契约。
- **FR-003**: 服务端 MUST 支持将实现了接口的业务类实例整体注册到
  Server：一次注册即发布该服务的全部方法；同一服务名重复注册 MUST
  被拒绝并返回明确错误。
- **FR-004**: 未被业务类重写的方法（继承自接口的默认实现）被调用时，
  系统 MUST 对客户端返回 UNIMPLEMENTED 状态，且不影响同服务其他方法。
- **FR-005**: 接口方法签名 MUST 通过调用上下文暴露取消通知与剩余时间
  查询，语义与既有能力一致（取消可感知、deadline 可查询）。
- **FR-006**: 代理 MUST 从 Channel 构造，MUST 提供同步与异步两种调用
  形态，且 MUST 可被多线程并发使用。
- **FR-007**: 生成的接口与代理 MUST 与框架现有消息类型（由既有 protobuf
  生成链产出）无缝衔接：方法签名直接使用这些消息类型，接口层不出现
  额外的消息复制层。
- **FR-008**: 生成物 MUST 纳入标准构建流程：服务描述变更后重新构建即
  得到更新后的接口与代理，无需手工步骤；生成 MUST 在三平台 CI 上
  确定性执行。
- **FR-009**: Channel MUST 仅表示连接（目标地址、建立、关闭）；关闭后
  其上全部代理的后续调用 MUST 立即以明确失败状态返回。业务接口
  （接口类与代理）MUST NOT 包含连接管理成员。
- **FR-010**: Client MUST 保留为控制面对象：承载连接/调用策略等控制
  功能的挂载点，业务接口不依赖其具体形态即可完成全部业务场景。
- **FR-011**: 生成器 MUST 复用既有构建链中的代码生成机制（同一描述
  格式、同一构建入口），不引入新的第三方运行时或生成期依赖。
- **FR-012**: 线协议行为 MUST 与本特性引入前完全一致：状态码映射、
  错误响应格式、deadline 传播保持不变，既有互操作测试全部继续通过。
- **FR-013**: 业务方法（重写的实现）内抛出的异常 MUST NOT 穿越框架
  边界；该次调用以 INTERNAL 状态结束，服务进程持续可用。
- **FR-014**: 既有面向 lambda/字符串路径的注册与调用入口 MUST 在本期
  保持可用（存量测试与用户代码不破坏）；新接口为推荐用法。

### Key Entities（关键实体）

- **服务描述（Service Description）**: 描述服务名、方法名与消息类型的
  契约文件；既是生成器输入，也是两端共享的单一事实来源。
- **服务端接口类（IXxxService）**: 由描述生成的纯虚接口；每个远程方法
  一个纯虚成员函数；是服务端业务类与客户端代理的共同基类。
- **业务实现类（XxxService）**: 用户继承接口类并重写方法的业务对象；
  以实例形式整体注册到 Server。
- **代理（XxxServiceProxy）**: 由描述生成、继承同一接口的客户端对象；
  将接口方法转译为经 Channel 的远程调用。
- **Channel（连接）**: 表示到目标服务的一条连接；负责地址、建立与
  关闭；不含业务语义。
- **Client（控制面）**: 客户端控制面对象；承载连接管理与后续控制策略
  的挂载点；与业务面（Proxy）解耦。
- **Server**: 服务端宿主；接受业务类实例的注册并对外发布其方法集合。

## 成功标准（Success Criteria）

### Measurable Outcomes

- **SC-001**: 以新接口实现并注册一个含 ≥2 方法的服务、经代理完成全部
  方法的同步与异步调用，端到端往返全部正确——示例与测试中无需出现任何
  方法名字符串。
- **SC-002**: 服务描述新增一个方法后，仅重新构建即可让服务端业务类在
  编译期被告知缺失实现、客户端获得新代理方法，全程无手工编辑生成物。
- **SC-003**: 全部受支持平台的标准构建、测试与示例流程在引入本特性后
  一次通过；既有互操作测试（与官方 gRPC 对端）结果保持全绿。
- **SC-004**: 新形态下实现示例服务端所需的用户代码行数不多于现形态的
  70%，且不再包含方法名/消息手工编解码代码。
- **SC-005**: 新接口层不引入任何新的第三方依赖，运行时依赖面与开发
  依赖面与本特性引入前完全一致。

## Assumptions

- 服务描述沿用既有 protobuf（.proto）格式与既有生成链（protoc +
  upb）；"工具"指在此链路上新增的接口/代理生成步骤，而非引入新的
  IDL。
- 一元（unary）方法仍是本阶段唯一支持的方法类型；流式方法的接口形态
  留待后续特性，但生成器命名与结构为其预留演进空间。
- Channel/Client/Proxy 的三分结构落在现有 C++ API 层内重整，内核
  （libuv/nghttp2/upb）不需要为接口重塑而改动。
- 存量的 lambda/字符串注册入口在本期标记为"兼容保留"，未来是否移除
  由后续宪法遵循的演进提案决定，本特性不承诺移除时间点。
- 生成代码为 C++17、纳入仓库忽略或生成目录（随构建产出），用户以
  include 方式消费；不提供独立 SDK 包形态。
